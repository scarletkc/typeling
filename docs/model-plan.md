# Plan: a small language model for typing prediction

Status: draft for review. Nothing in this document is implemented yet.

## 1. Goal

Publish a small English causal language model, about 30 MB after quantization, that predicts what a person is about
to type: the rest of the current word, the next word, and occasionally a few words. It must be usable on its own,
without this repository's autocomplete kernel: anyone should be able to load it with `transformers` or llama.cpp and
run it on a CPU.

Non-goals for v1: chat or instruction following, languages other than English, knowledge or reasoning benchmarks,
and on-device training.

Decisions so far:

| Question | Decision |
|---|---|
| Approach | the least-effort route: full-parameter continued pretraining of a recent small base model, not training from scratch |
| Base model | `SupraLabs/Supra-50M-Base`, subject to the check in milestone 0 |
| Size | about 30 MB: the release file is GGUF Q4_K_M; the fp16 weights are published as well |
| Data | v1 reuses the existing corpus in `data/corpus/`; more data only if the results show it is the bottleneck |
| Data licenses | permissive only (public domain, CC BY, ODC-By, Apache-2.0); no NC or share-alike data |
| Weights license | Apache-2.0 (the base model's license), with a NOTICE that carries the base model and dataset attributions |
| Typo-robust fine-tuning | included in v1 |
| Hardware | the local RTX 5070 Ti laptop GPU (12 GB); no rented GPUs |

## 2. Base model

Candidates checked on Hugging Face (quality claims on the community model cards are unverified):

| Model | Released | Parameters | Architecture | License | Pretraining data | Size at 4 bits | Verdict |
|---|---|---|---|---|---|---|---|
| SupraLabs/Supra-50M-Base | 2026-05 | 51.8M | `LlamaForCausalLM` | Apache-2.0 | FineWeb-Edu, 20B tokens | about 30 MB | **chosen**: newest model with a standard architecture and clean data |
| harrrshall/BarunLM-35M | 2026-07 | 35.1M | custom (needs remote code) | Apache-2.0 | 5.7B tokens, educational mix | about 20 MB | custom architecture makes export and quantization harder |
| MaliosDark/Isabel-50M | 2026-06 | 54.1M | `LlamaForCausalLM` | Apache-2.0 | educational text plus benchmark train splits | about 31 MB | fine-tuned on benchmark tasks, not a clean base |
| EleutherAI/pythia-31m | 2023 | 30.5M | `GPTNeoXForCausalLM` | Apache-2.0 | the Pile (includes Books3) | about 16 MB (31 MB at int8) | fallback; old, weak, unclear data provenance |
| HuggingFaceTB/SmolLM2-135M | 2024-11 | 134.5M | `LlamaForCausalLM` | Apache-2.0 | SmolLM corpus | about 70 MB | too large; used only as a reference |

Supra-50M-Base, per its model card: a general-purpose base model (no instruction tuning) meant for small-scale text
generation and as a fine-tuning starting point; vocabulary 32,000 (byte-level BPE trained on FineWeb-Edu), hidden
size 512, intermediate size 1,408, 12 layers, 8 attention heads with 4 KV heads, context 1,024, tied embeddings. Its
embedding matrix is about 16M of the 52M parameters. It was trained only on educational web text and evaluated only
on standard zero-shot benchmarks, so it knows nothing specific about chat or informal typing.

Expected file sizes: fp16 `safetensors` about 104 MB, GGUF Q4_K_M about 30 MB. Milestone 3 measures how much 4-bit
quantization costs.

## 3. Data

v1 uses the corpus already built for the n-gram model, with its dev and sealed test splits unchanged:

| Source | License | Kind | Training words |
|---|---|---|---|
| FineWeb | ODC-By 1.0 | web writing | 18.5M |
| SODA | CC BY 4.0 | everyday dialogue, generated by InstructGPT | 16.3M |
| WildChat-1M, user turns | ODC-By 1.0 | real typed text | 7.5M |
| Ubuntu IRC | Public Domain | informal internet chat | 4.4M |
| OpenAssistant oasst2, user turns | Apache-2.0 | real typed text | 0.4M |

About 47M words, roughly 60M tokens with the base tokenizer. Each chat turn or document is one segment, separated by
the base model's end-of-text token.

If the evaluation shows that more data would help, the next sources, in order of expected value: the remaining 30% of
WildChat user turns, the rest of SODA, CC BY YouTube transcripts (`common-pile/youtube_filtered`, spoken language),
more Ubuntu IRC, and CC BY news. New data from existing sources uses the same content-hash split, so the dev and test
splits do not change; any training document sharing a 13-gram with the dev or test splits is dropped.

## 4. Training

All stages are full-parameter (LoRA saves nothing meaningful at this size), bf16 mixed precision, AdamW, sequence
packing to 512 tokens, gradient clipping at 1.0.

1. **Continued pretraining.** Two to three epochs over the corpus (about 150–200M tokens), with the learning rate
   re-warmed to a fraction of a typical pretraining peak and decayed to zero. The decay phase weights the typing
   domains (real typed text, SODA, IRC) more heavily. FineWeb stays in the mix so general writing does not degrade.
2. **Typo-robust fine-tuning.** Two special tokens are added (`<|typed|>`, `<|word|>`; the embedding matrix is
   resized). Examples have the form `context <|typed|> noisy-prefix <|word|> intended-word`, where the noise model
   applies QWERTY adjacent-key substitutions, omissions, insertions, adjacent transpositions, missing apostrophes
   (dont, im) and casing errors; the context itself gets the same noise on about 5–10% of its words. These examples
   are mixed with clean language-modeling data so ordinary prediction does not degrade.
3. **Calibration.** Fit a temperature on the dev split so the word probabilities used by display thresholds are
   calibrated.

## 5. Quantization and export

- fp16 `safetensors` plus `config.json` and `tokenizer.json`, loadable with `transformers` as-is.
- GGUF Q4_K_M (via llama.cpp's converter, which supports the Llama architecture): the 30 MB release file.
- The Q4_K_M file is evaluated on the benchmark next to the fp16 weights; the model card reports the loss from
  quantization.

## 6. Decoding for typing

The model predicts tokens; the user needs words.

- Next word: a small beam (width 4–8, at most 4 steps) over continuations that start with a word-initial token and
  stop at a word boundary (a token that starts with a space or punctuation). The product of the step probabilities
  is the word's probability.
- Partially typed word: feed `<|typed|> prefix <|word|>` and decode the intended word with the same beam, so
  completion and correction (recie -> receive, tomm -> tomorrow) use one mechanism. Before the typo fine-tuning,
  fall back to prefix-constrained decoding: back off to the start of the word and allow only tokens consistent with
  the typed letters.
- Trailing spaces: with byte-level BPE the space belongs to the next token, so text ending in a space (the usual case
  before a next-word prediction) pushes the model toward rare tokens; the base model's own samples show this
  ("... is " continues with "iffy"). The decoder strips the trailing space from the context and requires the first
  generated token to start with a space.
- The context's key/value cache is reused across keystrokes.
- Latency target: at most 10 ms (p99) per suggestion with the Q4_K_M file on a laptop CPU.

## 7. Evaluation

- Benchmark: `bench/eval.py`'s typing simulation on the dev splits (chat, casual, writing), with the n-gram model's
  metrics: KSR, precision, suggestions shown, acc@0–3, top3@0. An adapter gives the LM the same `topk(text, k)`
  interface as `Predictor`.
- Language modeling: perplexity per word (normalized by words, not tokens).
- Baselines on the same benchmark: the bundled n-gram model (5 MB), the base model before fine-tuning, Pythia-31M and
  SmolLM2-135M (references only).
- Robustness: the benchmark with synthetic typos in the typed prefixes, before and after typo fine-tuning.
- Success criteria for v1 (targets to validate, not promises): with the Q4_K_M file on chat, at equal precision, KSR
  at least 3 points and acc@0 at least 5 points above the n-gram model; latency target met.
- The test splits stay sealed until the final comparison.

## 8. Compute

Training cost is about 6 × parameters × tokens: about 5e16 FLOPs for 52M parameters and 150M tokens, which is about an
hour on the RTX 5070 Ti laptop GPU at a realistic utilization; typo fine-tuning is smaller. Memory is not a
constraint. PyTorch with CUDA 12.8 or newer is required for this GPU (Blackwell); it is installed in an isolated uv
environment, never as a dependency of `word_predictor`.

## 9. Milestones

0. **Setup and gate.** Install PyTorch, write the typing decoder and the benchmark adapter, and evaluate the
   candidates zero-shot. Also check the trailing-space handling (section 6) and how finely the base tokenizer splits
   chat text (lowercase "i", slang such as lol and idk, contractions), measured in tokens per word on the dev splits.
   Gate: Supra-50M-Base should be at least on par with Pythia-31M; otherwise switch to the fallback.
1. Continued pretraining on the existing corpus.
2. Typo-robust fine-tuning.
3. Q4_K_M quantization and evaluation against the baselines.
4. Release: Hugging Face repository with fp16 weights, the Q4_K_M GGUF file, model card, NOTICE and the reference
   decoder.
5. Optional: more data (section 3), if milestone 3 shows the corpus is the bottleneck.
6. Optional: integration into the `word_predictor` kernel as an optional dependency.

Fallback if the fine-tuned base model disappoints: train a 15M-parameter model from scratch with a 16k BPE
tokenizer on an expanded corpus (the previous version of this plan, kept in git history).

## 10. Risks

- **Base model maturity.** Supra-50M-Base comes from a small lab, has few downloads and unverified benchmark claims;
  milestone 0 checks it before any training.
- **Domain shift.** The base model saw only educational web text; continued pretraining has to move it toward chat
  and informal typing, and the corpus is small.
- **4-bit quantization** may hurt a 50M-parameter model noticeably; milestone 3 measures it.
- **Base tokenizer** was trained on educational text and may split chat text into many small tokens, which costs
  context length and decoding steps; milestone 0 measures it.
- **SODA's origin.** It was generated by InstructGPT; OpenAI's terms restrict using outputs to build competing models.
  The risk for a typing model is small, but the model card must disclose it, and an ablation without SODA shows what
  it contributes.
- **Subword decoding** adds latency and complexity compared with the n-gram's word-level scoring; the latency target
  is the check.
- **Memorization and PII**: the corpus is already scrubbed of emails, URLs and phone numbers; test for verbatim
  reproduction of training text before release.

## 11. Repository layout

```text
lm/
  decode.py      typing decoder (beam over words, typed-prefix completion)
  eval.py        adapter that runs bench/eval.py's simulation on the LM
  data.py        tokenize data/corpus into packed shards with the base tokenizer
  typos.py       noise model for typo-robust fine-tuning
  train.py       continued pretraining and fine-tuning (PyTorch)
  export.py      safetensors, GGUF, model card
```

Training dependencies (torch, transformers, gguf) are declared as uv inline script metadata, never as runtime
dependencies of `word_predictor`.
